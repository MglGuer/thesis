\section{Knowledge Base Design}

Implemented in the architectural design is a structured knowledge base that stores scenarios, user profiles, and their corresponding conversation logs. The knowledge base is designed to support the personalization of advice and feedback by maintaining a comprehensive record of user metrics and interactions. The database schema includes the following:

\begin{itemize}
    \item \textbf{User Profiles} - Contains user information, primarily withholding personally identifiable information, and pragmatic competence metrics (Intention Coherence, Social Nuance, and Communicative Effectiveness) that are updated after each conversation session.
    \item \textbf{Conversation Logs} - Contains the transcripts of conversations corresponding to each user, along with the associated pragmatic analysis scores and feedback generated by the AI Mentor.
    \item \textbf{Scenarios} - Contains a collection of predefined conversational scenarios, each with its own context, goals, and dialogue data that the AI Partner uses for role-playing during conversations.
\end{itemize}

These tables are designed to be relational for querying and are primarily hosted in Supabase. The user profiles and conversation logs are linked via a foreign key relationship, as illustrated in Tables \ref{tab:user_profiles}, \ref{tab:conversation_logs}, and \ref{tab:scenarios_json}, while the scenarios are an independent JSON file loaded into the system.

The tables are initially unpopulated with user data; however, the scenarios table operates via an independent JSON catalogue containing a pre-defined set of conversational situations curated by the researchers. The user profiles are created upon registration, and the conversation logs are created sequentially after each session. 

A key architectural decision in the database design was the use of \texttt{JSONB} data types for the \texttt{session\_scores} and \texttt{mentor\_chat\_history} columns, rather than traditional relational normalization. This hybrid approach was chosen for three specific reasons:

\begin{enumerate}
    \item \textbf{Alignment with LLM Structured Outputs:} Since the Gemini 3 API natively supports Constrained Output via JSON Schema, the system receives a deeply nested object containing categories, numerical sub-scores, and long-form textual justifications. Storing this as a \texttt{JSONB} blob eliminates the impedance mismatch between the AI's hierarchical output and the database, removing the need for complex parsing logic that would be required to flatten the data into multiple relational tables.
    \item \textbf{Schema Flexibility and Evolution:} Pragmatic competence research is an evolving field. By using \texttt{JSONB}, the system is future-proofed; if future iterations of Socius incorporate new Gricean metrics or different pedagogical sub-categories, the database schema does not need to be migrated or altered. The system can simply store the new JSON structures immediately.
    \item \textbf{Atomic Data Fetching for UI Performance:} To render the Post-Session Feedback screen, the frontend requires the entire analysis block simultaneously. Storing the scores and justifications in a single \texttt{JSONB} column allows the backend to perform a single, atomic \texttt{SELECT} operation. This is significantly more efficient than executing multiple \texttt{JOIN} queries or aggregating several rows from a normalized scores table, thereby reducing latency in the feedback loop.
\end{enumerate}

For statistical tracking, while the complete evaluation is preserved in the \texttt{JSONB} blob, the Flask backend handles the extraction and normalization of the numerical values before updating the flat \texttt{avg\_} columns in the \texttt{User Profiles} table. These updates are then continuously averaged to track the user's progress over time and facilitate efficient longitudinal dashboard rendering.

\section{Software Design and Implementation}

The chatbot system is built on top of a large language model, Gemini 3 Flash, accessed via the \texttt{google-genai} SDK. It is implemented using Python with a Flask server backend and follows a dual-agent system architecture consisting of the AI Partner and the AI Mentor. In this architecture, the system orchestrates multiple instances of \texttt{gemini-3-flash-preview}, each configured with specific ``Thinking Budgets'' and system instructions to balance real-time latency with deep pragmatic analysis.

\subsection{Agent Instances and Configuration}
To achieve nuanced pedagogical feedback, the system utilizes four distinct configurations of Gemini 3 Flash:

\begin{itemize}
    \item \textbf{AI Partner (Roleplay):} Configured with a lower thinking budget (512 tokens), this instance prioritizes fast response times for fluid, real-time conversation while maintaining character persona.
    \item \textbf{AI Mentor (Pragmatic Analysis):} Configured with a high thinking budget (8000 tokens) to allow for computationally heavy analysis of user responses. It enforces a strict JSON schema that maps quantitative scoring to 3 core categories and 8 subcategories.
    \item \textbf{AI Mentor (Post-session Feedback):} Operates with a medium thinking budget (1,500 tokens) to generate human-readable, empathetic advice based on the rigid data provided by the Pragmatic Analysis instance.
    \item \textbf{Holistic Mentor:} Configured with a high thinking budget (8000 tokens), this agent focuses on aggregating longitudinal user data and conversation logs to provide holistic, targeted scenario recommendations.
\end{itemize}

\subsection{System Workflow}
The end-to-end user journey follows a strict sequence of operations:
\begin{itemize}
    \item \textbf{DOM Load:} The Document Object Model (DOM) loads the user interface built on HTML, CSS, and Flask.
    \item \textbf{Profile Initialization:} The system authenticates the user and initializes their profile, fetching quantitative metrics and historical data from Supabase.
    \item \textbf{Holistic Analysis:} The Holistic Mentor analyzes longitudinal metrics to recommend a scenario suited to the user's current developmental needs.
    \item \textbf{Scenario Selection:} The system loads the scenario catalogue into the UI, allowing the user to select a practice environment.
    \item \textbf{Load Dialogue Data:} Once selected, the system formats the interface to reflect the scenario's context, goals, and thematic conflict.
    \item \textbf{System Prompts:} The system initializes the AI Partner with the specific scenario constraints and persona instructions.
    \item \textbf{Active Conversation:} The user engages in real-time, streaming dialogue with the AI Partner.
    \item \textbf{Conversation End:} Upon completion, the system saves the raw transcript to the database and aligns the interaction data with the user's profile.
    \item \textbf{Pragmatic Analysis:} The AI Mentor evaluates the transcript using the quantitative scoring framework (Intention Coherence, Social \& Affective Nuance, Communicative Effectiveness) and delivers structured feedback.
    \item \textbf{In-depth Feedback:} The user may ask follow-up questions to the AI Mentor, which leverages the full conversation context to explain its scoring rationale.
\end{itemize}

The authentication screen allows users to sign in and have their profile data loaded. This accomplishes personalization, as the user's historical data becomes available for the Holistic Mentor to recommend scenarios based on their current needs. The profile also allows the user to view their progress over time across multiple conversations through the metric dashboard, while the overall pragmatic competence summary is accessible via the Profile Screen.

\subsection{Scenario Selection and Dialogue Loading}
 
The scenario selection subsystem is the entry point of every practice session. It is implemented as a two-phase process coordinated between the Flask backend and the client-side JavaScript.
 
In the first phase, when a user opens the new-chat modal, the browser issues a \texttt{GET} request to the \texttt{/api/scenarios} endpoint, which reads the \texttt{scenarios.json} file into memory. The catalogue is organized around four thematic conflicts drawn directly from the theoretical framework: \textit{Identity vs. Expectation}, \textit{Autonomy vs. Dependence}, \textit{Ambiguity vs. Definition}, and \textit{Group vs. Self}. As discussed in Chapter 4's Interface overview, the client renders these records as selectable cards in the scenario selection modal, grouped by thematic conflict so the user can identify which developmental challenge each scenario addresses.
 
In the second phase, once the user selects a scenario, the client sends a \texttt{POST} request to the \texttt{/api/start-session} endpoint. The backend instantiates a fresh \texttt{SociusChatbot} object, appending the scenario's full context to the base system instruction. It then inserts the AI Partner's opening line directly into the SDK's internal chat history so that it appears as an authentic model-turn rather than a synthetic user prompt. The session is stored in the server-side memory dictionary under a randomly generated session ID, and the client displays the opening message bubble to begin the conversation.

\subsection{AI Partner and Real-Time Conversation Flow}
 
The AI Partner is the conversational agent with which the user directly interacts during a practice session. It is implemented as a persistent chat session using the \texttt{google.genai} SDK's stateful \texttt{chats.create()} interface. This preserves the full multi-turn dialogue history natively within the SDK object, removing the need for the application to manually reconstruct conversation context on every API call.
 
The AI Partner instance is configured with three deliberate choices that reflect the system's pedagogical design. First, a thinking budget of 512 tokens is assigned to perform lightweight chain-of-thought reasoning, which is sufficient for cue-reading while keeping latency low. Second, the model's temperature is set to 1.0 to encourage naturalistic variation in dialogue. Third, the system instruction encodes specific rules for generating authentic Taglish speech, mandating Filipino conversational markers (\textit{diba}, \textit{kasi}) while adjusting formality based on the roleplayed persona.
 
Message delivery is implemented using Server-Sent Events (SSE) via the \texttt{/api/stream-message} endpoint. As discussed in Chapter 4's Interface overview, the generator function iterates over the response chunks as they arrive from the Gemini API, yielding each chunk as a JSON-encoded SSE frame. This creates a real-time typewriter effect on the frontend. A quota-aware retry wrapper monitors for rate-limit exceptions and transparently backs off before retrying, ensuring session stability under API pressure.
 
As a fault-tolerance mechanism, the client maintains a local copy of the full message history throughout the session. Should the server-side session expire before the user ends the conversation, the client supplies this local transcript enabling a stateless recovery path in the backend that reconstructs the scenario context and runs the pragmatic analysis without data loss.

\subsection{Pragmatic Logging and Post-Session Analysis}
 
Upon session termination, the system executes a two-stage routine that transforms the raw conversation transcript into structured pedagogical data and persists it to the database.
 
\textbf{Stage 1: Combined Analysis (Single API Call).} The pragmatic analysis is performed by a dedicated instance configured with a thinking budget of 8,000 tokens and a structured JSON output schema. The backend constructs a prompt by interpolating the scenario context and the transcript, instructing the model to produce both quantitative scores and qualitative feedback in a single generation pass to reduce API overhead.
 
The output is constrained to a JSON schema defining three category nodes: \textit{Intention Coherence}, \textit{Social \& Affective Nuance}, and \textit{Communicative Effectiveness}. Each category contains granular sub-scores and a string justification citing specific transcript evidence. Because the output is enforced as valid JSON via Gemini's native schema constraint, the backend parses the response reliably without any additional defensive processing.
 
\textbf{Stage 2: Database Persistence.} The Flask backend writes a new row to the \texttt{conversation\_logs} table, storing the transcript, the formatted feedback text, and the complete session scores JSON object. Simultaneously, the user's running average scores in the \texttt{user\_profiles} table are updated. The backend converts each raw 1--5 score to a 0.0--1.0 decimal and recalculates the cumulative running average. The updated profile metrics then become available to the Holistic Mentor. As discussed in Chapter 4's Interface overview, these persisted outputs drive the post-session feedback presentation.

\subsection{System Prompts and Theoretical Alignment}

The system prompts serve as the programmable cognitive core of the chatbot. They facilitate the role-playing of the AI Partner and the pedagogical evaluation generated by the AI Mentor. Rather than relying on generic AI behavior, these prompts strictly align the LLM's outputs with Grice's Maxims, Filipino Cultural Values, and the developmental frameworks of Havighurst and Arnett.

\subsubsection*{AI Partner Prompt}
The \texttt{AI\_PARTNER\_SYSTEM\_INSTRUCTION} focuses strictly on conversational realism and sociolinguistic accommodation. It instructs the model to embody a specific persona while abiding by strict constraints designed to prevent the LLM from sounding artificial.

\end{lstlisting}

\subsubsection*{AI Mentor Prompts (Analyzer vs. Chat)}
The AI Mentor is bifurcated into two distinct cognitive prompts to handle the complexity of pragmatic evaluation:

\textbf{1. The Analyzer Prompt:} Used strictly at the end of a session. It demands objective, evidence-based scoring and is heavily constrained to output only raw JSON data, stripping away conversational pleasantries.

\begin{lstlisting}[caption={Abridged AI Mentor Analyzer Prompt}, label={lst:analyzer_prompt}]
You are an expert socio-linguistic analyst. Provide your analysis in JSON format with two main sections:
1. pragmatic_scores: Score from 1-5 with sub-scores for Intention Coherence, Social Nuance, and Communicative Effectiveness.
2. feedback: Provide a key takeaway, cooperative efficiency, relational management, and an actionable tip.[CONVERSATION TRANSCRIPT INJECTED HERE]
\end{lstlisting}

\textbf{2. The Mentor Chat Prompt:} Used when the user clicks "Ask Mentor Why." This prompt shifts the persona back to a supportive figure. It is fed the raw JSON scores from the Analyzer and instructed to translate those rigid metrics into empathetic, natural language. 

\begin{lstlisting}[caption={Abridged AI Mentor Chat Prompt}, label={lst:mentor_chat_prompt}]
You are the AI Mentor - a warm, supportive Filipino mentor with a Kuya/Ate persona. 
STRICT FORMATTING RULES:
- DO NOT use markdown tables or raw JSON.
- Keep your answers concise and directly address the user's specific question.
- When explaining scores, summarize them conversationally.
- Be encouraging and constructive, not clinical or academic.
\end{lstlisting}

\subsubsection*{Holistic Mentor Prompt}
The \texttt{HOLISTIC\_MENU\_SYSTEM\_PROMPT} acts as the executive pedagogical layer. It takes the aggregated data from the user's database profile (session count, running averages, and calculated weakest competency) and formulates a tailored greeting that addresses their immediate learning needs.

\begin{lstlisting}[caption={Abridged Holistic Mentor Prompt}, label={lst:holistic_prompt}]
You are the "Holistic Mentor". Greet the user and suggest their next move based on their learning history.
USER STATS:
- Sessions: {session_count}
- Weakest Area: {weakest_area}

INSTRUCTIONS:
Suggest ONE specific Theme that addresses their weakest area. Explain WHY it will help them. Make it sound like a meaningful invitation, not an assignment.
\end{lstlisting}


\subsubsection*{Prompt Evolution and Engineering}
Initially, the system attempted to use a single, massive prompt to handle both roleplay and feedback simultaneously. Testing revealed this caused "persona bleed," where the AI Partner would suddenly offer academic critiques mid-conversation, breaking user immersion. 

The architecture evolved by splitting the responsibilities across different API instances and utilizing "Negative Constraints." Early iterations of the AI Mentor were overly critical, which negatively impacted the user's willingness to continue. By explicitly injecting the instruction to adopt a "warm, supportive Kuya/Ate persona" and structuring the feedback to always begin with a positive "Key Takeaway," the prompt engineering successfully balanced rigorous critique with empathetic delivery.

\subsection{User Interface Components and Their Computational Basis}
 
The front-end of Socius is a single-page application rendered by a Flask Jinja2 template. All views are toggled via CSS class manipulation and JavaScript state management. 
 
\textbf{Authentication and Profile Initialization.} The authentication flow is handled client-side using the Supabase JavaScript SDK. After the user authenticates, the client queries the backend for the user's running-average pragmatic scores, session count, and UI preferences to hydrate the interface.
 
\textbf{Holistic Mentor Greeting and Dashboard.} On the main menu screen, the system displays a personalized greeting. The backend calculates the user's weakest competency by finding the minimum non-zero value among the three dimensions, and computes sliding-window averages over the user's most recent sessions to classify their trajectory as \textit{improving}, \textit{plateaued}, or \textit{declining}. These statistics are passed to the Gemini API to generate the greeting text, which is then cached in the database to reduce API calls. The metric dashboard renders these same statistics as a line chart.
 
\textbf{Chats Sidebar and Conversation Replay.} The Chats sidebar queries the full \textit{conversation\_logs} table, parses each stored plaintext transcript back into individual message objects, and enriches each entry with the scenario title. When the user clicks a past chat, the client loads the full message list, scores, and any saved post-session mentor chat history, enabling complete replay.
 
\textbf{Post-Session Feedback Display.} After a session ends, the feedback screen renders a score panel showing the three category scores and their sub-scores, a narrative feedback section, and an ``Ask Mentor Why'' chat panel. When the user submits a question, the backend injects the full score JSON and the raw transcript into the mentor's chat history, ensuring subsequent mentor responses can cite specific utterances.
 
\textbf{Profile Screen.} The profile screen surfaces the user's display name, total sessions completed, and running-average pragmatic scores. A ``Reset Progress'' action zeroes all running averages and deletes all conversation logs for that user. UI customization options (dark mode, background selector) persist preferences directly to the database.

\subsection{Implicit Intent, Guardrails, and Safety Configuration}

Unlike traditional rule-based chatbots that require an explicit "Intent Detection" classification step to trigger pre-written responses, Socius relies on \textit{implicit intent}. The Gemini 3 Flash model is supplied with the entire conversational context and implicitly evaluates the user's speech acts to generate the next conversational turn dynamically.

Because the system accepts free-text input, mitigating out-of-scope topics, prompt injections, and inappropriate behavior (guardrails) is handled natively at the SDK level rather than via custom regular expressions. As shown in Listing \ref{lst:safety_settings}, Socius implements a strict array of \texttt{SafetySetting} objects passed to the \texttt{google.genai} API. To balance safety with the necessity of simulating realistic interpersonal conflicts (e.g., arguments, peer pressure), the threshold is calibrated to \texttt{BLOCK\_ONLY\_HIGH}.

\begin{lstlisting}[language=Python, caption={Safety Guardrails and Intent Handling via API Configuration}, label={lst:safety_settings}]
# Enforced across all AI Partner and AI Mentor interactions
DEFAULT_SAFETY_SETTINGS =[
    types.SafetySetting(
        category="HARM_CATEGORY_HARASSMENT", 
        threshold="BLOCK_ONLY_HIGH"
    ),
    types.SafetySetting(
        category="HARM_CATEGORY_HATE_SPEECH", 
        threshold="BLOCK_ONLY_HIGH"
    ),
    types.SafetySetting(
        category="HARM_CATEGORY_SEXUALLY_EXPLICIT", 
        threshold="BLOCK_ONLY_HIGH"
    ),
    types.SafetySetting(
        category="HARM_CATEGORY_DANGEROUS_CONTENT", 
        threshold="BLOCK_ONLY_HIGH"
    ),
]

FUNCTION generate_partner_response(user_input, current_history):
    # The LLM implicitly detects intent (e.g., refusal, question) 
    # and filters out-of-scope jailbreak attempts using the config above.
    INITIALIZE GeminiInstance WITH thinking_budget = 512, safety = DEFAULT_SAFETY_SETTINGS
    APPEND user_input TO current_history
    RETURN GeminiAPI.generate_content(system_instruction, current_history)
END FUNCTION
\end{lstlisting}

\subsection{Score Computation \& UI Transformation}

The LLM evaluates pragmatic competence on a 1-to-5 Likert scale. However, to display these metrics in a more engaging and accessible format on the frontend dashboard, the backend applies a mathematical transformation to convert the raw 1-5 scores into a 0.0-to-1.0 percentage format. 

\textbf{Equation 5.1: Score Normalization Formula}
$$Normalized\_Score = \frac{Score_{raw} - 1}{4}$$

Once normalized, the system calculates a cumulative running average to track the user's longitudinal progress in the database.

\textbf{Equation 5.2: Running Average Formula}
$$New\_Average = \frac{(Current\_Average \times Sessions\_Completed) + Normalized\_Score}{Sessions\_Completed + 1}$$

\subsection{Feedback Formatting \& Information Hierarchy}

To prevent overwhelming the user, the structured JSON payload generated by the schema in Listing \ref{lst:json_schema} is parsed by the backend and rendered into a hierarchical Markdown report. As demonstrated in Listing \ref{lst:feedback_format}, the raw JSON is unpacked; the "Key Takeaway" is surfaced immediately, while dense Gricean justifications are isolated in specific expandable panels on the UI.

\begin{lstlisting}[language=Python, caption={Parsing JSON into the Structured Frontend Report}, label={lst:feedback_format}]
FUNCTION _format_feedback_text(feedback_json_obj):
    IF feedback_json_obj is NULL: RETURN "No feedback available."
    
    parts =[]
    # 1. Surface the Tweet-sized takeaway immediately
    IF feedback_json_obj HAS "key_takeaway":
        parts.APPEND(feedback_json_obj["key_takeaway"])
        parts.APPEND("\n---\n")
    
    # 2. Extract Gricean analyses (Quantity, Quality, Relation, Manner)
    IF feedback_json_obj HAS "cooperative_efficiency":
        parts.APPEND("**1. Textual & Structural Clarity:**\n" + feedback_json_obj["cooperative_efficiency"])
        
    IF feedback_json_obj HAS "relational_management":
        parts.APPEND("**2. Social & Interpersonal Nuance:**\n" + feedback_json_obj["relational_management"])
        
    # 3. Surface practical application
    IF feedback_json_obj HAS "actionable_tip":
        parts.APPEND("**Actionable Tip:**\n" + feedback_json_obj["actionable_tip"])
        
    RETURN JOIN(parts, "\n")
END FUNCTION
\end{lstlisting}

\subsection{Holistic Mentor \& Progression Logic}

The Holistic Mentor analyzes the user's progress over multiple sessions. The system calculates a "Progression Trend" using a sliding window algorithm that compares the user's most recent sessions against past performance (Listing \ref{lst:progression_trend}). This ensures the system scaffolds the user toward their immediate learning needs in alignment with Vygotsky's Zone of Proximal Development.

\begin{lstlisting}[language=Python, caption={Progression Trend Algorithm}, label={lst:progression_trend}]
FUNCTION get_progression_trend(conversation_history, window=5):
    IF length(conversation_history) < 2:
        RETURN "insufficient_data"
        
    recent_sessions = GET_LAST(conversation_history, window)
    previous_sessions = GET_PREVIOUS(conversation_history, window)
    
    delta = AVERAGE(recent_sessions) - AVERAGE(previous_sessions)
    
    IF delta > 0.15:
        trend = "improving"
    ELSE IF delta < -0.15:
        trend = "declining"
    ELSE:
        trend = "plateaued"
        
    RETURN trend, delta, weakest_category
END FUNCTION
\end{lstlisting}

\section{LLM Selection and Architectural Pivot: The Fine-Tuning Experiment}

The objective was to create a specialized, cost-effective expert model trained exclusively on the GRICE dataset \cite{zheng_grice_2021} to identify conversational implicatures.

\subsection{Analysis of the Training Attempt}
The failure of the fine-tuned model provides valuable insights into the limitations of narrow dataset training for complex social coaching. The results yield three primary failure modes:

\begin{itemize}
    \item \textbf{Overfitting to Narrow Patterns:} The GRICE dataset consists of highly structured, short-form questions and answers. The model overfit to these patterns, learning superficial token transformations (e.g., simple subject-verb-object substitutions) rather than actual pragmatic reasoning.
    \item \textbf{Catastrophic Forgetting:} The nonsensical output (\textit{"I'm committed to keeping the living\_room tidy"}) demonstrated that the fine-tuning process caused the model to lose its general language modeling capabilities. It attempted to mimic the syntax of the dataset without preserving semantic understanding.
    \item \textbf{Loss of Long-Form Coherence:} The examples in the GRICE dataset are typically 10 to 30 words maximum. However, the AI Mentor requires the ability to generate over 1,000 words of coherent, structured prose. The fine-tuning process destroyed the model's ability to maintain extended reasoning chains.
\end{itemize}

Based on these findings, the architecture is pivoted away from local fine-tuning. Instead, the final system relies on sophisticated prompt engineering, structured JSON schemas, and the advanced dynamic reasoning capabilities (Thinking Budgets) of the Gemini 3 Flash model. This pivot demonstrates that for complex, theory-driven pedagogical tasks, the reasoning capacity of a generalist foundation model significantly outweighs the domain-specific knowledge gained by fine-tuning a smaller model on limited datasets.
