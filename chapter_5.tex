\chapter{Design and Implementation}\label{chap:chapter5}

\section{\hl{Knowledge Base Design}}

Implemented in the architectural design is a structured knowledge base that stores scenarios, user profiles, and their corresponding conversation logs. The knowledge base is designed to support the personalization of advice and feedback by maintaining a comprehensive record of user metrics and interactions. The database schema includes the following:

\begin{itemize}
    \item \textbf{User Profiles} - Contains user information, primarily withholding personally identifiable information, and pragmatic competence metrics (Intention Coherence, Social Nuance, and Communicative Effectiveness) that are updated after each conversation session.
    \item \textbf{Conversation Logs} - Contains the transcripts of conversations corresponding to each user, along with the associated pragmatic analysis scores and feedback generated by the AI Mentor.
    \item \textbf{Scenarios} - Contains a collection of predefined conversational scenarios, each with its own context, goals, and dialogue data that the AI Partner uses for role-playing during conversations.
\end{itemize}

These tables are designed to be relational for querying and are primarily hosted in Supabase. The user profiles and conversation logs are linked via a foreign key relationship, as illustrated in Tables \ref{tab:user_profiles}, \ref{tab:conversation_logs}, and \ref{tab:scenarios_json}, while the scenarios are an independent JSON file loaded into the system.

The scenarios catalogue is a static JSON file curated with scenarios that are designed by the research team. Thus, the population of this knowledge base is entirely manual and must be updated
through research proponents and expert working with each other to design a conversational scenario. It is never modified at runtime. Each scenario was manually authored to align with the different
aspects of the research' theoretical framework. The full\_description field encodes the AI Partner's persona and constraints. The data here is read-only, thereby
loaded into memory space on server startup and served directly from the Flask backend without any database round-trip.

The decision was made to use \texttt{JSONB} data types for the \texttt{session\_scores} and \texttt{mentor\_chat\_history} columns instead of fully normalizing the database. This hybrid approach was chosen for a few practical reasons.

First, because the Gemini 3 API natively outputs structured JSON based on the provided schema, saving the data directly as a \texttt{JSONB} object avoids the need to parse and distribute nested sub-scores across multiple relational tables. Second, it provides flexibility for future development; if subsequent iterations of Socius require adding or modifying pragmatic metrics, the database schema will not need to be migrated. Finally, this approach simplifies data retrieval. When the frontend loads the Post-Session Feedback screen, it can pull the entire analysis payload in a single query, rather than executing multiple \texttt{JOIN} operations to assemble the user's score.

For statistical tracking, while the complete evaluation is preserved in the \texttt{JSONB} blob, the Flask backend handles the extraction and normalization of the numerical values before updating the flat \texttt{avg\_} columns in the \texttt{User Profiles} table. These updates are then continuously averaged to track the user's progress over time and facilitate efficient longitudinal dashboard rendering.

        'scenario_id': scenario_id,
        'transcript': transcript,           # Raw conversation text
        'feedback_text': feedback_text,     # Formatted Markdown report

\subsection{\hl{Scenario Generation and Prompt Engineering}}

The scenario catalogue available to users is a collection of conversational contexts that are designed to elicit specific pragmatic challenges based on the theoretical framework proposed in this paper.
Each scenario is manually authored by the research team and is then further validated by the expert to ensure that the ecological validity, user engagement, and user safety objectives are met. These 
situations were generated by Gemini 3-pro and validated through the research proponents and the expert evaluator. The scenarios must be validated by an expert as the researchers do not have expertise in the different theoretical domains. This section
documents the evolution that suite went through in the process of prompt engineering and scenario design.

\subsubsection{Iteration 1 - Establishing Baseline Structure}

The first scenario established foundational scaffolding for scenario generation.

\begin{lstlisting}[caption={\hl{Iteration 1: Baseline Scenario Generation Prompt Utilizing Grice's Maxims}}, label=lst:iter1_prompt, numbers=left]
You are a chatbot that specializes in training an
individual's pragmatic skills by having the user
roleplay through a chosen scenario. Your task is to
generate 10 scenarios for each of Grice's Maxims
(Quantity, Quality, Relation, Manner) for a total of
40 scenarios. Make sure that all scenarios reflect
one or multiple Filipino cultural values
(Pakikisama, Hiya, Utang na Loob, Kapwa, Paggalang).
Also make sure that the scenarios are applicable and
relatable to young adults aged 15-24 in academic,
professional, or social contexts. Provide a title
for each scenario.
\end{lstlisting}

As shown in \textbf{Listing \ref{lst:iter1_prompt}}, the initial prompt instructed the language model to produce 40 scenarios based on Grice's Maxims \textbf{(Grice, 1975)}. While this iteration produced structurally consistent outputs grounded in recognizable everyday situations (e.g., missed lectures, internship feedback), two significant weaknesses emerged. First, the connection to Filipino cultural values was superficial. As seen in \textbf{Listing \ref{lst:iter1_prompt}, Lines 6--8}, the prompt only requested the model to \textit{``reflect one or multiple Filipino cultural values''} \textbf{(Jocano, 1997)}. Because this constraint was too broad, values such as \textit{Pakikisama}, \textit{Hiya}, and \textit{Utang na Loob} were only occasionally name-dropped as optional flavor text, rather than functioning as the core driver of the interpersonal conflict.

\subsubsection{Iteration 2 - Explicit Cultural Integration}

To address this cultural weakness, the prompt was revised in \textbf{Listing \ref{lst:iter2_prompt}}. To force the model to explicitly embed the cultural values into the conflict itself, a new constraint was added in \textbf{Listing \ref{lst:iter2_prompt}, Lines 11--12}, which commands the model to \textit{``make the Scenario description rich.''} This revision ensured that the cultural values functioned as active constraints on how the user must respond. For instance, where the prompt in \textbf{Listing \ref{lst:iter1_prompt}} might tag a scenario with `Utang na Loob' as an afterthought, the targeted revision in \textbf{Listing \ref{lst:iter2_prompt}} ingrained the debt of gratitude as a core feature of the situation the user must navigate.

\begin{lstlisting}[caption={\hl{Iteration 2: Scenario Generation Prompt with Explicit Cultural Value Constraints}}, label=lst:iter2_prompt, numbers=left]
You are a chatbot that specializes in training an
individual's pragmatic skills by having the user
roleplay through a chosen scenario. Your task is to
generate 10 scenarios for each of Grice's Maxims
(Quantity, Quality, Relation, Manner) for a total of
40 scenarios. Make sure that all scenarios reflect
one or multiple Filipino cultural values
(Pakikisama, Hiya, Utang na Loob, Kapwa, Paggalang).
Also make sure that the scenarios are applicable and
relatable to young adults aged 15-24 in academic,
professional, or social contexts. Additionally, make
the Scenario description rich. Provide a title for
each scenario.
\end{lstlisting}

This revision deepened cultural grounding. The cultural values and influences are now built into the conflict, allowing for the goal of each scenario to be locally catered to the Filipino emerging adult context. However, quality deterioration was still present and because the scenarios were limited to the rule of
of "one maxim per scenario", the scenarios didn't naturally simulate real lived experiences as multiple maxims are being flouted and are present in each conversation. This artificially constrained the complexity of the scenarios and arguably reduced their ecological validity.


\subsubsection{Iteration 3 - Removing the Single-Maxim Constraint}

To resolve the unnatural constraints of single-maxim violations, \textbf{Listing \ref{lst:iter3_prompt}} introduces a new design rule. As shown in \textbf{Listing \ref{lst:iter3_prompt}, Lines 6--8}, the model is explicitly instructed: \textit{``You do not have to specifically categorize the scenarios per Maxim - a scenario can tackle multiple maxims at once.''} This allows for more complex, naturalistic scenarios that better reflect real-world pragmatic challenges. As such, the number of scenarios was reduced to 10 to check if the depth and quality of the output would improve with fewer scenarios to generate.

\begin{lstlisting}[caption={\hl{Iteration 3: Removing the Single-Maxim Constraint and Adding Explicit Output Formats}}, label=lst:iter3_prompt, numbers=left]
You are a chatbot that specializes in training an
individual's pragmatic skills by having the user
roleplay through a chosen scenario. Your task is to
generate 10 scenarios for each of Grice's Maxims
(Quantity, Quality, Relation, Manner) for a total of
40 scenarios. You do not have to specifically categorize
the scenarios per Maxim - a scenario can tackle multiple
maxims at once. Make sure that all scenarios reflect
one or multiple Filipino cultural values
(Pakikisama, Hiya, Utang na Loob, Kapwa, Paggalang).
Also make sure that the scenarios are applicable and
relatable to young adults aged 15-24 in academic,
professional, or social contexts. Additionally, make
the Scenario description rich. Provide a title, maxims
tackled, user role, and chatbot role, for each scenario.
\end{lstlisting}


This next iteration introduced as well a different principled design rule wherein the chatbot should be the initiator of the pragmatic conflict. Rather than placing, the user in a neutral position and asking them to respond appropriately, the chatbot was now specifically configured to violate
on or more maxims through its opening statement. Thus, the navigation of the user with the scenario would be more reactive and dynamic, allowing the user to try and understand the implied meaning behind the chatbot's utterance while considering scenario context. The user's new task then was to manage this violation 
skillfully while respecting Filipino cultural norms, which is a design that is more representative of real-life situations.

Moreover, as the prompt was engineered to instead create 10 scenarios instead of 40, the quality of the output had a direct correlation to content exclusion. Scenarios became more deeply personal and relatable in the eyes of the research proponents as the model was able to take inspiration from lived experiences and cultural narratives. This however reduced the diversity of the scenarios.
A comment made on the current suite of the scenarios was that while these were ecologically valid, they did not necessarily constitute for being a scenario that can teach the user pragmatic competence. There was no clear learning opportunity in the scenario design.


\subsubsection{Havighurst's Developmental Tasks and Arnett's Emerging Adulthood Themes}

To ensure the scenarios provided genuine ``teachable moments'' \textbf{(Havighurst, 1948)} and reflected the psychosocial instability of youth \textbf{(Arnett, 2000)}, the prompt was overhauled. The theoretical framework was revised to explicitly integrate Havighurst's Developmental Tasks and Arnett's Emerging Adulthood themes into the scenario design. The combination of which led the team to create four themes that combine both theories and integrate Grice's Maxims and Filipino Cultural Values.

\textbf{Listing \ref{lst:themes}, Lines 5--12} demonstrates how Theme 1 was explicitly codified to pit an emerging adult's personal desire against familial expectation, forcing a pragmatic negotiation of \textit{Utang na Loob}. These formulas were then injected into the final synthesized prompt, as seen in \textbf{Listing \ref{lst:iter4_prompt}, Lines 12--16}, which structurally maps each developmental task to a specific Gricean and cultural conflict.

\begin{lstlisting}[caption={\hl{Four Integrated Thematic Conflict Formulas Based on Havighurst and Arnett}}, label=lst:themes, numbers=left]
# Havighurst: the life task the user is navigating.
# Arnett:     the psychological context that makes that task feel unstable
#             or high-stakes.

# THEME 1: "Identity vs. Expectation"
# Conflict: Personal desire/identity vs. family or societal expectation.
# Dynamic:  Authenticity (Arnett) vs. Obligation (Utang na Loob, Paggalang)
# Formula:
# 1. The user is developing a personal [goal, value, career path, or identity].
# 2. An authority figure expresses a [conflicting expectation or disappointment].
# 3. The situation forces the user to [defend, explain, or conceal] their choice.
# Goal: Validate the authority's perspective while asserting their own identity.

# THEME 2: "Autonomy vs. Dependence"
# Conflict: Desire for adult independence vs. being treated as a dependent.
# Dynamic:  Independence (Arnett) vs. Hierarchy (Paggalang, Family Roles)
# Formula:
# 1. The user [living at home, financially dependent] makes an [adult decision].
# 2. A guardian [parent, older sibling, boss] [questions or overrules] it.
# 3. The user must justify their competence without being childishly defiant.
# Goal: Shift the conversation from "obedience" to "responsibility."

# THEME 3: "Ambiguity vs. Definition"    [... same structure ...]
# Conflict: Unclear emotional or relational boundaries.
# Dynamic:  Clarity (Grice's Maxims) vs. Fear of Loss (Pakikisama, Kapwa)
# Formula:  1. Ambiguous relationship.  2. Trigger event.  3. DTR conversation.
# Goal: Express feelings with honesty (Quality) and kindness (Manner).

# THEME 4: "Group vs. Self"              [... same structure ...]
# Conflict: Peer group values vs. personal integrity or ethics.
# Dynamic:  Group Harmony (Pakikisama) vs. Personal Integrity (Kapwa, Hiya)
# Formula:  1. Peer group acts unethically.  2. Silence implies agreement.
#           3. User chooses: stay silent, intervene, or confront.
# Goal: Intervene in a way that minimizes defensiveness to de-escalate.
\end{lstlisting}


Each theme was given an explicit conflict formula and a defined communicative goal, ensuring that scenario generation remained consistent and pedagogically purposeful regardless of which specific situation was written. This produced a formula that scenario generation could follow. 

\subsubsection{Iteration 4 - Synthesis of Theoretical Frameworks and Design Principles}

The fourth and final iteration synthesized all prior theoretical layers into a coherent thematic taxonomy as seen above. 


\begin{lstlisting}[caption={\hl{Iteration 4: Final Synthesized Prompt Combining Developmental Tasks, Filipino Values, and Gricean Maxims}}, label=lst:iter4_prompt, numbers=left]
You are a specialized chatbot designer and developmental psychology expert.
Generate 10 rich roleplaying scenarios for Filipino adolescents and young adults
(ages 15-24) grounded in Havighurst's Developmental Tasks and Arnett's Theory
of Emerging Adulthood.

THEMATIC FRAMEWORK:
Each scenario must combine:
  Havighurst's Developmental Task -> the life task the user is navigating.
  Arnett's Psychological Context  -> the emotional instability that makes
                                     this task ambiguous or high-stakes.

Align each scenario with one of four integrated themes:
  Theme 1 "Identity vs. Expectation": Authenticity vs. Utang na Loob
  Theme 2 "Autonomy vs. Dependence":  Responsibility vs. Paggalang
  Theme 3 "Ambiguity vs. Definition": Grice's Clarity vs. Pakikisama
  Theme 4 "Group vs. Self":           Pakikisama vs. Personal Integrity

FORMAT PER SCENARIO:
  Title, Theme, Primary Developmental Task (verbatim, Havighurst 1972),
  Maxims Tackled, Cultural Values, User Role, Age Range, Chatbot Role,
  Rich Scenario Description, Expected Pragmatic Skill

GENERATION RULES:
  1. Implicit Task Design: never reveal the communication goal directly.
  2. Cultural Sensitivity: respect hierarchies, indirectness, harmony.
  3. Variety: include both adolescent (12-18) and early adult (19-24).
  4. Balance: distribute scenarios evenly across the four themes.
  5. Authenticity: conflicts must feel natural and emotionally real.
\end{lstlisting}


This then produced a final suite of 10 scenarios that explicitly follows the revised theoretical framework and design principles all-the-while targetting the intended learning outcomes and audience. Thus, the constraints for scenario generation were set and produced the final scenario catalogue that is to be evaluated by the expert. 
Critically, the chatbot-as-conflict-initiator principle from Iteration 3 was retained and further refined. In the final suite, the chatbot's opening utterance is calibrated not only to violate a specific maxim but to do so in a manner that is culturally loaded. This is seen by the violation itself being expressed through a distinctly Filipino communicative act, such as
the mother's use a photo of family dog as a passive-aggressive check-in that violates the Maxim of Manner while invoking Paggalang in Filipino Cultural Values. This design ensures that the communicative skill the user must practice is inseperable from the Filipino social context.


\section{\hl{Software Design and Implementation}}

The chatbot system is built on top of a large language model, Gemini 3 Flash, accessed via the \texttt{google-genai} SDK. It is implemented using Python with a Flask server backend and follows a dual-agent system architecture consisting of the AI Partner and the AI Mentor. In this architecture, the system orchestrates multiple instances of \texttt{gemini-3-flash-preview}, each configured with specific ``Thinking Budgets'' and system instructions to balance real-time latency with deep pragmatic analysis.

\subsection{\hl{Agent Instances and Configuration}}
To achieve nuanced pedagogical feedback, the system utilizes four distinct configurations of Gemini 3 Flash:

\begin{itemize}
    \item \textbf{AI Partner (Roleplay):} Configured with a lower thinking budget (512 tokens), this instance prioritizes fast response times for fluid, real-time conversation while maintaining character persona.
    \item \textbf{AI Mentor (Pragmatic Analysis):} Configured with a high thinking budget (8000 tokens) to allow for computationally heavy analysis of user responses. It enforces a strict JSON schema that maps quantitative scoring to 3 core categories and 8 subcategories.
    \item \textbf{AI Mentor (Post-session Feedback):} Operates with a medium thinking budget (1,500 tokens) to generate human-readable, empathetic advice based on the rigid data provided by the Pragmatic Analysis instance.
    \item \textbf{Holistic Mentor:} Configured with a high thinking budget (8000 tokens), this agent focuses on aggregating longitudinal user data and conversation logs to provide holistic, targeted scenario recommendations.
\end{itemize}

\subsection{\hl{System Workflow}}
The end-to-end user journey follows a strict sequence of operations:
\begin{itemize}
    \item \textbf{DOM Load:} The Document Object Model (DOM) loads the user interface built on HTML, CSS, and Flask.
    \item \textbf{Profile Initialization:} The system authenticates the user and initializes their profile, fetching quantitative metrics and historical data from Supabase.
    \item \textbf{Holistic Analysis:} The Holistic Mentor analyzes longitudinal metrics to recommend a scenario suited to the user's current developmental needs.
    \item \textbf{Scenario Selection:} The system loads the scenario catalogue into the UI, allowing the user to select a practice environment.
    \item \textbf{Load Dialogue Data:} Once selected, the system formats the interface to reflect the scenario's context, goals, and thematic conflict.
    \item \textbf{System Prompts:} The system initializes the AI Partner with the specific scenario constraints and persona instructions.
    \item \textbf{Active Conversation:} The user engages in real-time, streaming dialogue with the AI Partner.
    \item \textbf{Conversation End:} Upon completion, the system saves the raw transcript to the database and aligns the interaction data with the user's profile.
    \item \textbf{Pragmatic Analysis:} The AI Mentor evaluates the transcript using the quantitative scoring framework (Intention Coherence, Social \& Affective Nuance, Communicative Effectiveness) and delivers structured feedback.
    \item \textbf{In-depth Feedback:} The user may ask follow-up questions to the AI Mentor, which leverages the full conversation context to explain its scoring rationale.
\end{itemize}

The authentication screen allows users to sign in and have their profile data loaded. This accomplishes personalization, as the user's historical data becomes available for the Holistic Mentor to recommend scenarios based on their current needs. The profile also allows the user to view their progress over time across multiple conversations through the metric dashboard, while the overall pragmatic competence summary is accessible via the Profile Screen.

\subsection{\hl{Scenario Selection and Dialogue Loading}}
 
The scenario selection subsystem is the entry point of every practice session. It is implemented as a two-phase process coordinated between the Flask backend and the client-side JavaScript.
 
In the first phase, when a user opens the new-chat modal, the browser issues a \texttt{GET} request to the \texttt{/api/scenarios} endpoint, which reads the \texttt{scenarios.json} file into memory. The catalogue is organized around four thematic conflicts drawn directly from the theoretical framework: \textit{Identity vs. Expectation}, \textit{Autonomy vs. Dependence}, \textit{Ambiguity vs. Definition}, and \textit{Group vs. Self}. As discussed in Chapter 4's Interface overview, the client renders these records as selectable cards in the scenario selection modal, grouped by thematic conflict so the user can identify which developmental challenge each scenario addresses.
 
In the second phase, once the user selects a scenario, the client sends a \texttt{POST} request to the \texttt{/api/start-session} endpoint. The backend instantiates a fresh \texttt{SociusChatbot} object, appending the scenario's full context to the base system instruction. It then inserts the AI Partner's opening line directly into the SDK's internal chat history so that it appears as an authentic model-turn rather than a synthetic user prompt. The session is stored in the server-side memory dictionary under a randomly generated session ID, and the client displays the opening message bubble to begin the conversation.

\subsection{\hl{AI Partner and Real-Time Conversation Flow}}
 
The AI Partner is the conversational agent with which the user directly interacts during a practice session. It is implemented as a persistent chat session using the \texttt{google.genai} SDK's stateful \texttt{chats.create()} interface. This preserves the full multi-turn dialogue history natively within the SDK object, removing the need for the application to manually reconstruct conversation context on every API call.
 
The AI Partner instance is configured with three deliberate choices that reflect the system's pedagogical design. First, a thinking budget of 512 tokens is assigned to perform lightweight chain-of-thought reasoning, which is sufficient for cue-reading while keeping latency low. Second, the model's temperature is set to 1.0 to encourage naturalistic variation in dialogue. Third, the system instruction encodes specific rules for generating authentic Taglish speech, mandating Filipino conversational markers (\textit{diba}, \textit{kasi}) while adjusting formality based on the roleplayed persona.
 
Message delivery is implemented using Server-Sent Events (SSE) via the \texttt{/api/stream-message} endpoint. As discussed in Chapter 4's Interface overview, the generator function iterates over the response chunks as they arrive from the Gemini API, yielding each chunk as a JSON-encoded SSE frame. This creates a real-time typewriter effect on the frontend. A quota-aware retry wrapper monitors for rate-limit exceptions and transparently backs off before retrying, ensuring session stability under API pressure.
 
As a fault-tolerance mechanism, the client maintains a local copy of the full message history throughout the session. Should the server-side session expire before the user ends the conversation, the client supplies this local transcript enabling a stateless recovery path in the backend that reconstructs the scenario context and runs the pragmatic analysis without data loss.

\subsection{\hl{Pragmatic Logging and Post-Session Analysis}}
 
Upon session termination, the system executes a two-stage routine that transforms the raw conversation transcript into structured pedagogical data and persists it to the database.
 
\textbf{Stage 1: Combined Analysis (Single API Call).} The pragmatic analysis is performed by a dedicated instance configured with a thinking budget of 8,000 tokens and a structured JSON output schema. The backend constructs a prompt by interpolating the scenario context and the transcript, instructing the model to produce both quantitative scores and qualitative feedback in a single generation pass to reduce API overhead.
 
The output is constrained to a JSON schema defining three category nodes: \textit{Intention Coherence}, \textit{Social \& Affective Nuance}, and \textit{Communicative Effectiveness}. Each category contains granular sub-scores and a string justification citing specific transcript evidence. Because the output is enforced as valid JSON via Gemini's native schema constraint, the backend parses the response reliably without any additional defensive processing.
 
\textbf{Stage 2: Database Persistence.} The Flask backend writes a new row to the \texttt{conversation\_logs} table, storing the transcript, the formatted feedback text, and the complete session scores JSON object. Simultaneously, the user's running average scores in the \texttt{user\_profiles} table are updated. The backend converts each raw 1--5 score to a 0.0--1.0 decimal and recalculates the cumulative running average. The updated profile metrics then become available to the Holistic Mentor. As discussed in Chapter 4's Interface overview, these persisted outputs drive the post-session feedback presentation.

\subsubsection*{Prompt Evolution and Engineering}
Initially, the system attempted to use a single, massive prompt to handle both roleplay and feedback simultaneously. Testing revealed this caused "persona bleed," where the AI Partner would suddenly offer academic critiques mid-conversation, breaking user immersion. 

The architecture evolved by splitting the responsibilities across different API instances and utilizing "Negative Constraints." Early iterations of the AI Mentor were overly critical, which negatively impacted the user's willingness to continue. By explicitly injecting the instruction to adopt a "warm, supportive Kuya/Ate persona" and structuring the feedback to always begin with a positive "Key Takeaway," the prompt engineering successfully balanced rigorous critique with empathetic delivery.

\subsection{\hl{Implicit Intent, Guardrails, and Safety Configuration}}

Unlike traditional rule-based chatbots that require an explicit "Intent Detection" classification step to trigger pre-written responses, Socius relies on \textit{implicit intent}. The Gemini 3 Flash model is supplied with the entire conversational context and implicitly evaluates the user's speech acts to generate the next conversational turn dynamically.

Because the system accepts free-text input, mitigating out-of-scope topics is handled via the \texttt{\_try\_generate\_with\_rotation} wrapper (\textbf{Listing \ref{lst:implicit_intent}, Lines 6--8}), while prompt injections, and inappropriate behavior (guardrails) is handled natively at the SDK level rather than via custom regular expressions. As shown in \textbf{Listing \ref{lst:safety_settings}, Lines 3--18}, Socius implements a strict array of \texttt{SafetySetting} objects passed to the API with the threshold calibrated to \texttt{BLOCK\_ONLY\_HIGH} (\textbf{Listing \ref{lst:safety_settings}, Line 5}).

\textit{Theoretical Justification:} Because conversational implicature (Grice, 1975) relies on context rather than rigid keywords, the AI Partner uses implicit intent resolution. Instead of classifying a user's message into a static intent bucket (e.g., \texttt{INTENT\_REFUSAL}), the model parses the speech act dynamically based on the scenario constraints. 

Below is the structure of how the user's input is passed to the Gemini 3 Flash model, and the format of the generated Taglish response which inherently contains the conversational intent:

\subsection{\hl{Score Computation \& UI Transformation}}

The LLM evaluates pragmatic competence on a 1-to-5 Likert scale. However, to display these metrics in a more engaging and accessible format on the frontend dashboard, the backend applies a mathematical transformation to convert the raw 1-5 scores into a 0.0-to-1.0 percentage format. 

\textbf{Equation 5.1: Score Normalization Formula}
$$Normalized\_Score = \frac{Score_{raw} - 1}{4}$$

Once normalized, the system calculates a cumulative running average to track the user's longitudinal progress in the database.

\textbf{Equation 5.2: Running Average Formula}
$$New\_Average = \frac{(Current\_Average \times Sessions\_Completed) + Normalized\_Score}{Sessions\_Completed + 1}$$

These mathematical models are implemented within the backend Python logic (\textbf{Listing \ref{lst:running_avg_computation}, Lines 14--18}) to continuously track user progress. Furthermore, the frontend utilizes React components (\textbf{Listing \ref{lst:star_rating_ui}, Lines 4--16}) to visually transform these normalized scores into an intuitive 5-star rating interface for the user.

\begin{lstlisting}[language=Python, caption={\hl{Python Backend Running Average Computation}}, label=lst:running_avg_computation, numbers=left]

raw_sn = scores['social_affective_nuance']['score']
raw_ce = scores['communicative_effectiveness']['score']

# 2. Convert from 1-5 scale to 0.0-1.0 (Normalization)
new_ic_score = (raw_ic - 1) / 4
new_sn_score = (raw_sn - 1) / 4
new_ce_score = (raw_ce - 1) / 4

# 3. Calculate new running averages
def calculate_running_average(current_avg, completed_count, new_value):

new_ic_avg = calculate_running_average(current_ic_avg, sessions_completed, new_ic_score)

def _format_feedback_text(self, feedback_obj):
    """Formats the structured feedback JSON into readable Markdown text."""
    if not feedback_obj:
        return "No feedback available."
    
    parts =[]
    
    # 1. Surface the Tweet-sized takeaway immediately
    if feedback_obj.get("key_takeaway"):
        parts.append(feedback_obj["key_takeaway"])
        parts.append("\n---")
    
    # 2. Extract and format Gricean/Sileo analyses
    struct = feedback_obj.get("cooperative_efficiency")
    if struct:
        parts.append(f"**1. Textual & Structural Clarity:**\n{struct}\n")
    
    inter = feedback_obj.get("relational_management")

        parts.append(f"**2. Social & Interpersonal Nuance:**\n{inter}\n")

    # 3. Surface practical application
    if feedback_obj.get("actionable_tip"):
        parts.append(f"**Actionable Tip:**\n{feedback_obj['actionable_tip']}")
    
    return "\n".join(parts)

\subsection{\hl{Holistic Mentor \& Progression Logic}}

The Holistic Mentor analyzes the user's progress over multiple sessions. The system calculates a ``Progression Trend'' using a sliding window algorithm that compares the user's most recent sessions against past performance (\textbf{Listing \ref{lst:progression_trend}, Lines 2--9}). This ensures the system scaffolds the user toward their immediate learning needs in alignment with Vygotsky's Zone of Proximal Development.

\begin{lstlisting}[language=Python, caption={\hl{Progression Trend Algorithm}}, label=lst:progression_trend, numbers=left]
def get_progression_trend(self, window=5):
    history = self.get_conversation_scores_history()
    
    if len(history) < 2:
        return {
            'trend': 'insufficient_data',
            'session_count': len(history),
            'latest_scores': history
        }
    
    def extract_overall(entry):
        s = entry.get('scores', {})
        ic = s.get('intention_coherence', {}).get('score') or 0
        sn = s.get('social_affective_nuance', {}).get('score') or 0
        ce = s.get('communicative_effectiveness', {}).get('score') or 0
        return {'ic': ic, 'sn': sn, 'ce': ce, 'overall': (ic + sn + ce) / 3}
    
    all_scores =[extract_overall(h) for h in history]
    
    # Calculate streak of improvement
    streak = 0
    for i in range(len(all_scores) - 1, 0, -1):
        if all_scores[i]['overall'] > all_scores[i - 1]['overall']:
            streak += 1
        else:
            break
    
    # Compare recent window to previous window
    recent = all_scores[-window:]
    previous = all_scores[-2 * window:-window] if len(all_scores) >= 2 * window else all_scores[:max(1, len(all_scores) - window)]
    
    def avg_dict(lst):
        if not lst: return {'overall': 0}
        return {'overall': sum(d['overall'] for d in lst) / len(lst)}
    
    recent_avg = avg_dict(recent)
    prev_avg = avg_dict(previous)
    
    delta_overall = round(recent_avg['overall'] - prev_avg['overall'], 3)
    
    # Determine trend based on overall delta
    THRESHOLD = 0.15  # ~3% change on the 1-5 scale
    if delta_overall > THRESHOLD:
        trend = 'improving'
    elif delta_overall < -THRESHOLD:
        trend = 'declining'
    else:
        trend = 'plateaued'
    
    return {
        'trend': trend,
        'delta': {'overall': delta_overall},
        'streak': streak
    }
\end{lstlisting}

\subsection{\hl{Analysis of the Training Attempt}}
Evaluating the fine-tuned Mistral-7B model revealed several practical issues with using a narrow dataset for social coaching. Three main problems were observed during testing:

First, the model tended to overfit to the structure of the dataset. Because the GRICE dataset relies on short, highly structured question-and-answer pairs, the fine-tuned model learned to perform simple word substitutions rather than applying actual pragmatic reasoning.

Second, the fine-tuning process degraded the model's baseline conversational abilities. For example, when prompted to analyze a passive-aggressive statement about a dirty kitchen, the model outputted, ``I'm committed to keeping the living room tidy.'' This indicates the model was attempting to mimic the syntax of the training data at the expense of basic contextual understanding.

Finally, the fine-tuned model struggled to maintain long-form coherence. While the training examples usually maxed out at 30 words, the AI Mentor role requires generating much longer, coherent feedback. The model frequently lost its train of thought during extended reasoning chains.

Ultimately, these results led to the abandonment of local fine-tuning. It was found that utilizing the existing reasoning capabilities of a larger generalist model (Gemini 3 Flash) through prompt engineering was a much more reliable approach for this specific pedagogical use case.
